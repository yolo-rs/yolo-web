# Browser Engine Rewrite and Upstream Integration Plan

## Evidence-based starting point

YOLO-Web currently contains a Bun-hosted CDP workbench and a Rust workspace with Servo-derived and browser-adjacent crates. It does not contain Chromium's browser process, `content/`, Blink, V8 checkout, Skia, Dawn, Chromium `third_party/`, GN graph, or `DEPS`-resolved dependency tree. The workbench uses an external browser endpoint. A crate catalog, a CDP client, or a V8 isolate is not a browser engine. `crates/yolo-chromium` now runs upstream Chromium through CEF's official binary distribution (Chromium 156), which gives the repository a runnable native shell but still no Chromium source tree; see the [CEF adapter boundary](CEF_ADAPTER_BOUNDARY.mdx).

This distinction defines the rewrite. The source of truth for a Chromium-based product must be a real Chromium checkout and its own dependency/build machinery. Do not rebuild a lookalike engine by independently vendoring libraries that Chromium already pins and patches. The Chromium checkout docs use `depot_tools`/`fetch`/`gclient`; GN generates Ninja build files. Chromium's own architecture puts browser UI and I/O in the browser process, with web content rendered in sandboxed renderer processes using Blink. See the [source tree guide](https://www.chromium.org/developers/how-tos/getting-around-the-chrome-source-code/) and [official checkout/build instructions](https://chromium.googlesource.com/chromium/src/+/main/docs/get_the_code.md).

## Product boundary

The target product is a Chromium embedder with a Rust control plane, not a Rust reimplementation of Blink. Chromium's supported extension points and process boundary remain authoritative:

- The C++ embedder owns `content/` integration, browser process lifetime, windows, profiles, navigation, permissions, downloads, and platform integration.
- Blink, V8, Skia, Dawn/Tint, `net/`, `cc/`, sandbox, ICU, codecs, and other Chromium dependencies are built from the same Chromium revision selected by `DEPS` and GN. Dawn identifies itself as Chromium's WebGPU implementation; Skia documents its Chromium roll relationship and warns against mixing its independent dependency graph into Chromium.
- Rust owns bounded services where it adds value: policy, automation orchestration, research/benchmark runners, test tooling, and selected isolated components. Cross-process communication should use a reviewed IPC boundary (Mojo or a deliberately versioned bridge); Rust must not bypass renderer sandboxing or pretend to replace browser-process security policy.
- Bun hosts developer tools, MCP, dashboards, and local orchestration. It is not the renderer, web platform implementation, or browser kernel.
- Servo, WebKit/JSC, and Firefox/Gecko stay separately versioned benchmark targets. Shared WPT and benchmark harnesses may compare them, but engine-specific behavior and capabilities must remain visible.

This follows Chromium's documented process model: browser process for UI and I/O, renderer process for page content, with Blink inside the renderer. See [Chromium multi-process architecture](https://www.chromium.org/developers/design-documents/multi-process-architecture/) and [Blink's project documentation](https://www.chromium.org/blink/). Servo's own book says its embeddable webview work is ongoing and currently recommends `servoshell` as the browser demonstration, so Servo integration must be tracked as an engine target rather than claimed as a finished view library ([Servo Book](https://book.servo.org/)).

## Repository shape to converge on

Keep the orchestration repo small enough to maintain and keep upstream's multi-repository graph intact. A Chromium working checkout is generated by `fetch` and `gclient`, not committed as a nested submodule or copied into `vendor/` by hand.

```text
yolo-web/                         # orchestration, product-specific source, Rust/Bun
  apps/
    human-browser/                # Bun CDP API/media service; yolo-ui owns its frontend
    ai-agent-runner/              # Bun/Rust automation orchestration
  src/                             # planned YOLO-Web-owned native C/C++ sources by component
  crates/
    browser-policy/               # Rust policy/service components with explicit IPC boundary
    yolo-chromium/                # CEF-based Chromium shell over the official binary distribution (current)
    browser-bench/                # benchmark orchestration and result schema
  packages/
    cdp-client/                   # CDP for tooling; not renderer integration
    chromium-tracker/             # versions, channels, patch and build metadata
  third_party/                    # only separately reviewed direct dependencies; not Chromium DEPS
  patches/chromium/<milestone>/   # reviewed, ordered, upstreamable patch queue + metadata
  build/                          # reproducible wrapper configs, never replacement GN files
  docs/

../chromium/                      # official fetch workspace; ignored and disposable
  .gclient                        # gclient root config
  src/DEPS                        # authoritative third-party revisions
  src/third_party/blink/          # Blink source
  src/third_party/dawn/           # Dawn/Tint source as pinned by Chromium
  src/third_party/skia/           # Skia source as pinned by Chromium
  src/out/<config>/               # GN/Ninja build outputs; ignored
```

Do not duplicate Chromium's `third_party/` into this repository. Chromium's `DEPS` file and `gclient sync` are the lockfile and checkout mechanism for its dependency graph. For a patch that also needs an upstream Skia/Dawn/Blink change, make the coordinated upstream change and update the corresponding Chromium roll/DEPS pin instead of silently using a second dependency revision. See [Skia in Chromium](https://docs.skia.org/docs/dev/chrome/) and [building Dawn](https://dawn.googlesource.com/dawn/).

## Build and source workflow

1. Install the platform-supported toolchain and official `depot_tools` from the [Chromium get-the-code guide](https://chromium.googlesource.com/chromium/src/+/main/docs/get_the_code.md). Use yolo-cross for Windows/Linux qualification, MSVC diagnostics, and Rust cross-compilation; keep Chromium source builds on their pinned native toolchains.
2. Create the source tree with `fetch chromium`; do not clone only `src` and do not replace `gclient sync` with `git submodule update`.
3. Record the Chromium Git revision, branch/channel, `DEPS` state, toolchain versions, GN args, and patch queue revision in an engine lock manifest. A build must be reproducible from that lock.
4. Generate an output directory with `gn gen` and inspect effective args with `gn args <out> --list`; build the smallest target first with `autoninja -C <out> <target>`, then build the product shell.
5. Keep build output, downloaded CIPD assets, profiles, symbols, and user data out of Git. Avoid checking in generated vendored source or a user's `.gclient` credentials/configuration.
6. Rebase the ordered product patch queue on each selected upstream milestone. Every patch needs upstream path, upstream commit, owner, rationale, license/provenance, test evidence, and removal condition. Prefer small upstreamable changes; keep downstream-only branding and integration patches isolated.

The exact commands, supported flags, and system requirements vary by platform and Chromium revision; use the pinned checkout's own docs and `DEPS`, not stale copied instructions. Official references: [Chromium build instructions](https://chromium.googlesource.com/chromium/src/+/main/docs/) and [depot_tools](https://chromium.googlesource.com/chromium/tools/depot_tools/).

## Milestones and acceptance evidence

1. **Truthful browser service and UI ownership** (service split implemented): identify the external CDP browser from `Browser.getVersion`, expose navigation/evaluation/status/media through the YOLO-Web API, and host the responsive workbench frontend in yolo-ui. Evidence: yolo-web CDP tests and yolo-ui proxy/render tests with mock endpoints.
2. **Reproducible upstream checkout** (pending): automated fetch/sync from a pinned official Chromium revision on Windows and Linux; verify `gclient revinfo`, clean `DEPS` state, disk/toolchain prerequisites, and an unmodified upstream build target.
3. **Native Chromium shell** (implemented) as a CEF-based Rust shell (`crates/yolo-chromium`, boundary in [CEF_ADAPTER_BOUNDARY.mdx](CEF_ADAPTER_BOUNDARY.mdx)) rather than the C++ `content` embedder first planned: the launcher prepares a runtime directory and starts CEF's bootstrap host, which loads the `yolo-chromium` cdylib with Chromium's sandbox enabled, owns the browser, renderer, GPU, and utility processes, exposes the initial URL, the profile (`--cache-path`), and an optional `--remote-debugging-port`, and shows the Chrome runtime style with the Views toolbar, omnibox, DevTools, and popups as new windows. Ordinary browsing needs no separately launched browser or DevTools port. Evidence: the smoke receipt `engines/cef.lock.json` written by `cargo run -p yolo-chromium -- --smoke --url=chrome://version/ --receipt=engines/cef.lock.json`. Still missing versus a `content/` embedder: a YOLO-Web-owned tab strip and tab model, extension loading, a CEF build from the pinned Chromium `159.0.8143.0` checkout (the shell runs CEF's binary distribution of Chromium `156.0.8078.80`), Linux x64 qualification, and the yolo-ui host test from the adapter's integration gate.
4. **Rust/Bun integration** (pending): reviewed, typed, versioned IPC/API for automation and policy; process-isolation tests prove that a renderer cannot gain host filesystem/network privileges through the integration.
5. **Upstream engine patch loop** (pending): machine-readable milestone/branch locks, DEPS roll reports, patch applicability checks, Chromium try/build/test jobs, and upstream submission metadata.
6. **Cross-engine research and benchmarks** (pending): WPT-backed conformance plus repeatable startup, navigation, memory, rendering, WebGPU, and automation benchmarks across Chromium, Firefox Nightly, WebKit/JSC, and Servo, with per-engine versions and raw artifacts.

No milestone is complete because a document or catalog entry exists. Completion requires the build/runtime evidence listed above.
