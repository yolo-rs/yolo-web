## CEF and Rust bindings

CEF's official [branch/build guide](https://github.com/chromiumembedded/cef/blob/master/docs/branches_and_building.md) says its `master` follows Chromium master and is for development, while numbered release branches track individual Chromium milestones. Its [`automate-git.py` workflow](https://github.com/chromiumembedded/cef/blob/master/docs/chromium_update.md) downloads a separate depot_tools/Chromium/CEF workspace and maintains a patch series. A CEF binary therefore does not reuse `${CHROMIUM_ROOT}/src` merely because the milestone matches.

The community [`tauri-apps/cef-rs`](https://github.com/tauri-apps/cef-rs) bindings are the Rust dependency of `crates/yolo-chromium`. The published `cef` package includes `cef-dll-sys` and versioned CEF API bindings; the pinned release `156.3.0` targets Chromium 156, and its build script downloads CEF's own binary distribution into the git-ignored `.cef/` cache. No CEF 159 binding or artifact matching the local checkout exists yet. Keep CEF's platform-specific runtime distribution separate from the Chromium source build.

## Skia and Canvas

Chromium's product Canvas path is Blink plus the Skia revision selected by the Chromium checkout's `DEPS`. The [`rust-skia` project](https://github.com/rust-skia/rust-skia) is useful for Rust experiments, but its branch is independently versioned and its build machinery may sync dependencies or download binary archives. Pinning `skia-safe` alone does not make it ABI-compatible with Chromium's Skia library.

Keep the existing `tiny-skia` Obscura renderer and Servo Canvas as named comparison implementations. A later `skia-safe` adapter must be built against the exact `DEPS` Skia revision and GN configuration, have a narrow C ABI boundary, and pass image/conformance comparison on Windows 11 and Linux x64 before any product renderer switches to it.

## Downstream patch reuse

Brave publishes explicit Chromium version-upgrade and patching workflows: [version upgrades](https://github.com/brave/brave-core/blob/master/docs/chromium_version_upgrade.md) and [patching Chromium source](https://github.com/brave/brave-core/blob/master/docs/patching_and_chromium_src.md). Helium publishes its current Chromium base in [`chromium_version.txt`](https://github.com/imputnet/helium/blob/main/chromium_version.txt). These are provenance and rebase references, not drop-in patches. For each imported patch, record its source branch/commit, Chromium base, local conflicts, license, owner, validation, and removal condition under [`patches/chromium/`](../patches/chromium/README.mdx).

## Update procedure

1. The official Chromium `gclient sync --nohooks` is complete for the public configuration. Capture `git rev-parse HEAD`, `chrome/VERSION`, `DEPS`, and `gclient revinfo --actual --output-json -`. Keep `--snapshot` out of the public source-lock path while it attempts absent private DEPS entries.
2. Read the V8 and Skia pins from that `DEPS`, not from a separate Cargo package or an engine version label.
3. Compare Electron, CEF, Brave, Helium, Node/V8, and Rust binding revisions to that exact checkout. Record exact commits and milestone/build numbers.
4. Rebase one downstream patch family at a time and keep its native build/test workflow separate from Bun's repository workflow.
5. Do not claim consolidation complete until the same Chromium build passes with the selected patches and the CEF/engine benchmarks report their independent binary/source versions.
